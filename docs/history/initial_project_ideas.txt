# 1. Fine-tuning / LoRA / PEFT Ideas

### 1. When Does LoRA Fail? Understanding Rank Allocation Across Layers

**Research question:** Is uniform LoRA rank allocation across all transformer layers optimal?

Idea:

* Standard LoRA uses the same rank everywhere.
* Investigate adaptive allocation:

  * higher rank in attention layers
  * higher rank in MLP layers
  * rank based on gradient importance
  * rank based on activation statistics

Compare:

* Full fine-tuning
* Standard LoRA
* AdaLoRA
* Your adaptive rank strategy

**Datasets:** GLUE, SuperGLUE, GSM8K or domain-specific QA.

**Why interesting:** Goes beyond simply applying LoRA and asks a fundamental efficiency question.

**Novelty potential:** High enough for a course project.

---

### 2. Can Small LLMs Learn Better Through Layer-Selective Fine-Tuning?

Instead of adapting every layer, investigate:

> Which layers actually need adaptation for different tasks?

Experiments:

* Fine-tune only early layers
* Only middle layers
* Only later layers
* Different combinations

Measure:

* Performance
* Trainable parameters
* Training time
* Memory

**Scientific question:**

> Does task complexity determine where adaptation should occur in an LLM?

This is simple but can produce a surprisingly strong analysis paper.

---

### 3. LoRA Initialization Strategies

Most people use standard initialization without thinking much about it.

Investigate whether better initialization can improve:

* convergence speed
* low-rank adaptation quality
* stability under very low ranks

Compare:

* Random initialization
* SVD-based initialization
* Activation-aware initialization
* Gradient-informed initialization

Potentially propose a lightweight initialization technique.

# 2. Mixture of Experts (MoE)

### 4. Can You Build Task-Specialized Experts Using LoRA?

This is a particularly nice project concept.

Instead of training a massive MoE:

1. Start with one base LLM.
2. Train multiple LoRA adapters as "experts":

   * reasoning expert
   * coding expert
   * summarization expert
   * mathematical expert
3. Train/design a router.
4. Route each input to the appropriate LoRA expert.

Research question:

> Can parameter-efficient LoRA experts approximate the benefits of mixture-of-experts architectures?

Compare:

* Base model
* Single general LoRA
* Random expert routing
* Oracle routing
* Learned routing

This is feasible without training a huge MoE from scratch.

---

### 5. Soft vs Hard Routing for LoRA Experts

Build several domain/task-specific adapters.

Compare:

**Hard routing**

```
Input → Router → Expert 3
```

vs

**Soft routing**

```
Input → Router → 0.2 Expert 1 + 0.7 Expert 2 + 0.1 Expert 3
```

Research questions:

* Does soft routing improve generalization?
* How many experts are actually useful?
* What happens for ambiguous inputs?

Nice combination of:

* MoE
* PEFT
* routing
* efficiency

---

### 6. Router Collapse in Small MoE Systems

MoE routers sometimes route too many samples to a few experts.

Investigate:

> How effective are different load-balancing strategies in preventing expert collapse?

Experiment with:

* auxiliary load balancing loss
* entropy regularization
* noisy routing
* temperature scaling

Metrics:

* task accuracy
* expert utilization entropy
* load imbalance
* inference cost

This is more research-oriented.

# 4. Hallucination

### 10. Detecting Hallucinations Without External Knowledge

Instead of RAG, ask:

> Can we detect hallucinations using only the model's internal generation behavior?

Possible signals:

* token entropy
* disagreement across samples
* hidden-state similarity
* contradiction between generated answers
* attention patterns

Compare with:

* self-consistency
* external fact verification
* existing hallucination detection methods

Datasets:

* TruthfulQA
* HaluEval

This has a clear evaluation setup.

### 11. Adaptive Retrieval for RAG

Most RAG systems retrieve for **every query**.

But many queries don't need retrieval.

Build:

```text
Query
  ↓
Need Retrieval?
 ↙️          ↘️
No           Yes
↓             ↓
LLM          Retriever → LLM
```

Research question:

> Can adaptive retrieval reduce cost and hallucination without hurting answer quality?

Methods for deciding retrieval:

* model confidence
* query classification
* entropy
* small routing classifier

Metrics:

* accuracy
* hallucination rate
* retrieval frequency
* latency

Very practical and publishable-style.

# 5. RAG Ideas

### 12. Does Better Retrieval Always Mean Better Generation?

A very interesting question.

Experiment with retrieval quality:

```
Perfect retrieval
High-quality retrieval
Moderate retrieval
Noisy retrieval
Contradictory retrieval
```

Then measure generation quality.

Research question:

> How robust are LLMs to imperfect or conflicting retrieved information?

Datasets:

* Natural Questions
* HotpotQA
* MuSiQue

Metrics:

* Recall@K
* EM/F1
* answer faithfulness

This allows a very systematic study.

---

### 13. Query-Adaptive Chunking for RAG

Standard RAG chunks documents into fixed sizes:

```
512 tokens
1024 tokens
2048 tokens
```

Instead:

> Can chunk size dynamically depend on query complexity?

Example:

* Simple factual query → small chunk
* Multi-hop question → larger context
* Broad conceptual query → multiple chunks

Compare against fixed chunking.

This has practical novelty and manageable implementation complexity.

---

### 14. Reranking vs More Retrieval

Question:

> With a fixed computational budget, should we retrieve more documents or retrieve fewer and rerank them?

Compare:

```text
Top 5 retrieval
Top 20 retrieval
Top 50 retrieval

vs

Top 50 → Reranker → Top 5
```

Measure:

* retrieval quality
* answer quality
* latency

Simple but rigorous.

### 18. Teacher–Student Distillation With Difficulty-Aware Data

Standard knowledge distillation treats examples equally.

Idea:

1. Use a large teacher.
2. Estimate example difficulty.
3. Train a smaller student with a curriculum:

   * easy → medium → difficult

Compare:

* Random ordering
* Easy-to-hard curriculum
* Hard-example emphasis

Question:

> Does difficulty-aware distillation improve small LLM reasoning?

## One important recommendation

For this kind of course proposal, **don't chase novelty for novelty's sake**. The strongest projects usually have this structure:

> **Clear scientific question → simple hypothesis → controlled experimental setup → strong baselines → quantitative analysis → small proposed improvement**

For example, this is much stronger than *"We will build an MoE LLM"*:

> **"Can task-specialized LoRA adapters combined through learned routing achieve better multi-task performance than a single LoRA adapter under an equivalent parameter budget?"**

That single sentence already gives you:

* objective
* hypothesis
* baselines
* methodology
* evaluation direction
